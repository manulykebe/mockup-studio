Generic ASM Field Extraction: Procedure Synopsis

Goal: turn any Allotrope ASM measurement file into a linearized dataset (rows of label, value, unit) by joining it against a reviewable field catalog, without hardcoding field names per instrument.

Always, first

  1. Read the measurement file.
  2. Extract $asm.manifest (a URI string at the top level).

If the manifest is new (no cached catalog yet)

  1. Resolve the manifest URI: strip the scheme and host, then look up in/manifest/<remaining path> (e.g. the manifest http://purl.allotrope.org/manifests/ftir/REC/2024/12/ftir.manifest resolves to in/manifest/ftir/REC/2024/12/ftir.manifest, still plain JSON content despite the extensionless name), matched by its @id, then read its json-schemas[0] URI.
  2. Resolve that schema URI the same way: strip the scheme and host, then look up in/schema/<remaining path> (e.g. http://purl.allotrope.org/json-schemas/adm/ftir/REC/2024/12/ftir.schema resolves to in/schema/adm/ftir/REC/2024/12/ftir.schema), matched by its $id.
  3. Run scripts/schema_catalog_builder.js on that schema to produce a catalog of every candidate field, with value: null and an include flag pre-set (true for scalar/quantity, false for datacube). Its output defaults to in/catalog/schema_field_catalog.json.
  4. Manually review the catalog: adjust include flags as needed, then save it under a name keyed to the manifest in in/catalog/ (e.g. in/catalog/<manifest-name>.catalog.json). Never reuse the reserved name field_catalog.schema.json - that file is the JSON Schema validating the catalog format itself, not a catalog.

If the manifest is already known (cached catalog exists)

  1. Resolve the manifest URI the same way, to confirm it matches the cached catalog's manifest.
  2. Load the existing cached catalog directly - skip regeneration.

Always, last: the "join"

  1. Run node scripts/dataset_extractor.js in/<measurement-file> in/catalog/<schema-catalog> -o out/dataset.csv -j out/joined_field_catalog.json -t <title>.
  2. For each catalog entry with include: true, resolve its path against the live measurement file and emit a typed datum row.
  3. The optional -j output is the schema catalog populated with live measurement values, units, and datacube sizes. Missing schema-defined paths are retained for traceability with value: null and include: false.

What the join means

The schema catalog describes what a measurement can contain: field names, paths, units, types, and the fields selected for output. It is a template, not the measurement result.

The join matches each selected catalog path with the same path in the actual measurement file. It then copies the current value and unit from the measurement into the catalog entry. Fields defined by the schema but missing from this measurement are kept for traceability and marked include: false.

For scientists, this means the selected results are taken from the actual experiment while the schema supplies their meaning and expected units. For developers, it means the schema catalog supplies the field selection and paths, and the measurement file supplies the live data. The final CSV is a flat view of the joined result: one row per label, value, and unit.

Worked example: the available FTIR file

The available measurement file is in/00237_NIR005_G017_water_S0995945_S01.001.asm. Its extension is .asm, but its content is JSON, so the Node.js scripts can read it directly with JSON.parse.

  1. Read the top-level $asm.manifest value: http://purl.allotrope.org/manifests/ftir/REC/2024/12/ftir.manifest.
  2. Resolve that URI to the local manifest: in/manifest/ftir/REC/2024/12/ftir.manifest. Its @id matches the measurement's manifest URI.
  3. Read json-schemas[0] from the manifest: http://purl.allotrope.org/json-schemas/adm/ftir/REC/2024/12/ftir.schema.
  4. Resolve that URI to: in/schema/adm/ftir/REC/2024/12/ftir.schema, then verify its $id matches the schema URI.
  5. Build the schema catalog: 
    node scripts/schema_catalog_builder.js in/schema/adm/ftir/REC/2024/12/ftir.schema
    This writes 33 candidate fields to in/catalog/schema_field_catalog.json. Its values are null because the catalog was built from the schema.
  6. For this example, use the reviewed data catalog generated from the measurement file, or use the schema catalog as the template: 
    node scripts/dataset_extractor.js in/00237_NIR005_G017_water_S0995945_S01.001.asm in/catalog/schema_field_catalog.json -o out/dataset-from-schema.csv -j out/joined_field_catalog.json -t 00237_NIR005_G017_water_S0995945_S01.001
    The schema catalog remains the selection/template contract; the extractor populates its actual values and units from the measurement. This writes 15 selected linearized rows to out/dataset-from-schema.csv and the populated template to out/joined_field_catalog.json.

For example, the schema entry for Fourier transform infrared document.measurement document.aperture size setting starts with value: null and unit: "nm". After the join it contains value: 0 and unit: "nm", while its schema metadata and path are retained.

The schema catalog is the reusable selection template. After manual review, its include flags can be used with future measurements that use the same manifest and schema. The extractor always takes the current value and unit from the measurement file, not from the schema catalog's null placeholders.

Key clarifications

  • The manifest does not contain a schema directly - it only points to one via a URI, which must be matched to a local .schema file by $id.
  • The catalog's path and include fields control selection. The measurement's current value and unit populate the joined entry, replacing the schema catalog's null value placeholder.
  • The CSV columns are Title, Datum Label, Index, typed scalar value columns, Unit, Ontology, and the pipe-delimited parent Path. Numeric values currently use Scalar Double Datum; the title comes from -t or falls back to the measurement's sample identifier.
  • Catalogs must be cached per manifest, under distinct filenames, to avoid collisions with reserved schema files.

Folder layout

  • in/ - measurement files (read-only inputs).
  • in/manifest/ - manifest files, stored under a path that mirrors their $asm.manifest URI exactly (host stripped, path kept, no extension added - still JSON content).
  • in/schema/ - ASM schema files, stored under a path that mirrors their $id URI (host stripped, path kept).
  • in/catalog/ - schema-derived field catalogs (reviewable, before joining).
  • scripts/ - the three Node.js tools described below.
  • out/ - generated catalogs and the linearized dataset (all script outputs).

Tooling map

Script Input Output Purpose
scripts/catalog_builder.js in/<measurement file> (.asm.json) out/field_catalog.json Discover fields from an actual data file (values populated)
scripts/schema_catalog_builder.js in/schema/<schema file> (.schema) in/catalog/schema_field_catalog.json Discover fields from a schema (no data yet, values null)
scripts/dataset_extractor.js in/<measurement file> + in/catalog/<schema catalog> out/dataset.csv + optional out/joined_field_catalog.json Populate the schema template from a measurement and emit linearized rows
